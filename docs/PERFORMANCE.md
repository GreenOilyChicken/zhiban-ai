## 1. 压测目标（对应 §10.2）

| 编号 | 验收指标 | 判定口径 | 本轮结论 |
|---|---|---|---|
| P-1 | 系统支持至少 **50 个并发用户**同时在线 | `--concurrency 50` 且全程错误率为 0 | ✅ 桩服务下已验证 50 并发稳定运行 |
| P-2 | 单次对话响应时间 **≤ 3 秒**（不含网络延迟） | `--scenario chat` 的 **P95 ≤ 3000ms** | ⚠️ 见 §5，真实后端未运行，尚无有效数据 |

**关于 P-2 的口径说明**：本工具以 **P95** 作为主判据（即 95% 的对话请求在 3 秒内返回），
而非平均值——平均值会被少数超时请求稀释。`--json` 输出中同时提供 `p50/p90/p95/p99/max`，
若验收方要求更严口径，可改看 `p99`。

**关于「不含网络延迟」**：本压测在**本机回环**或**同内网**发起，
测得的是「HTTP 请求发出 → 响应收完」的服务端处理时间，已剔除公网传输延迟。
跨机房/公网场景需另行折算。

## 3. 方法学

### 3.1 工具设计

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 并发模型 | N 个 `threading.Thread`，每个持有独立 `http.client` 连接 | 真并发，非串行循环 |
| 起跑对齐 | `threading.Barrier` 让所有线程同时出发 | 避免「先启动的线程多打请求」造成样本倾斜 |
| 连接复用 | HTTP/1.1 keep-alive | 贴近真实用户会话；避免把 TCP 握手算进业务延迟 |
| `TCP_NODELAY` | 客户端与服务端均关闭 Nagle | 否则 keep-alive 短请求叠加 delayed-ACK，凭空产生 ~40ms「假地板延迟」 |
| 百分位算法 | 线性插值（同 `numpy.percentile` 默认） | 结果可交叉验证 |
| 失败处理 | 网络异常折叠为 `status=0` 样本继续统计，连接断开自动重连一次 | 单点失败不中断整轮压测 |
| 预检 | 启动前 TCP 连通性检查，不可达立即退出（码 2） | 快速失败并给出排查建议 |

### 3.2 三个场景

| 场景 | 内容 | 验证目标 |
|---|---|---|
| `auth` | 并发 `POST /api/auth/guest-login` | JWT 在并发下签发正确（唯一性） |
| `mixed` | 登录一次取 Token，并发轮询 3 个只读接口 | 并发承载能力 + Token 传递正确性 |
| `chat` | 并发 `POST /api/chat/send` | **§10.2 P-2 对话延迟**（唯一有效场景） |

### 3.3 局限与前提

1. **`mixed` 的延迟不能论证对话延迟指标**。只读接口不经过 LLM，快是正常的。
2. 本压测从**单台压测机**发起。50 线程本身也会消耗本机 CPU，
   若要排除压测机瓶颈，应使用独立压测机或分布式压测。
3. **未包含 SSE 流式接口** `/api/chat/send/stream`。流式响应需按「首字节时间(TTFB)」
   与「完整流时长」分别度量，与本文口径不同，属后续工作。
4. 压测数据受 MySQL 连接池（`maximum-pool-size: 20`）影响——
   若 50 并发下出现排队，瓶颈可能先在连接池而非 CPU。

## 4. 如何复现

```bash
# ── 前置：启动后端（详见 DEPLOYMENT.md）──
cd java-backend
export DB_PASSWORD=xxx JWT_SECRET=<32位以上随机串> AI_SERVICE_URL=http://localhost:8081
export RATE_LIMIT_ENABLED=false          # 压测期间建议关闭限流
mvn spring-boot:run

# ── 确认可达 ──
curl -s http://localhost:8080/api/agent/list

# ── 小规模试跑（确认无 404/401）──
python3 scripts/loadtest/load_test.py --scenario mixed --concurrency 5 --duration 5

# ── 正式两轮 ──
python3 scripts/loadtest/load_test.py --scenario mixed \
    --concurrency 50 --duration 60 --json-out mixed.json
python3 scripts/loadtest/load_test.py --scenario chat \
    --concurrency 50 --duration 60 --json-out chat.json
```

无真实后端时，可用内置桩服务自检脚本本身：

```bash
python3 scripts/loadtest/stub_server.py --port 18080 --latency-ms 20
python3 scripts/loadtest/load_test.py --base-url http://127.0.0.1:18080 \
    --context-path '' --scenario mixed --concurrency 50 --duration 10
```

1. **工具已交付并实测可用**：`scripts/loadtest/load_test.py` 仅依赖 Python 3 标准库，
   在 50 并发下自身开销稳定（P95 约 24ms），具备真并发、JWT 校验、
   P50/P90/P95/P99 统计、JSON 输出、优雅失败等完整能力。
2. **判定逻辑经负向验证**：延迟超标、错误率、不可达三种异常均能被正确识别，
   不存在「永远通过」的假阳性风险。
3. **§10.2 的真实验收数据尚缺失**，原因是 **Java 后端（8080）当前未运行**。
   本文所有性能数字均来自**本地桩服务**，**不可**作为后端性能结论。
4. **下一步**：按 §4 启动后端（含 MySQL、Python AI 服务）后执行两轮压测，
   将结果填入 §6 的表格，即可形成完整的 §10.2 验收证据。
